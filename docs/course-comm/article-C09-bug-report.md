# 回報 bug：把提問與講重點合起來

回報 bug 是測試工程師最高頻的溝通行為，也是前面兩套技巧的完美交會點。一份好的 bug 報告，本質上同時在做兩件事：

- 它是一次**提問**——你在請工程師幫你定位與修復，所以提問的所有原則都適用（環境、重現步驟、已做努力）。
- 它是一次**講重點**——你要讓對方在三秒內接收到「這多嚴重、影響誰」，所以講重點的原則也適用（聚焦、有益、同理）。

把這兩套合起來，就是一份讓工程師看完立刻想處理、而不是皺眉反問的 bug 報告。

## 一份 bug 報告的骨架

把提問與講重點的元素對應到報告的各欄位：

- **標題（講重點）**：用目標—差異格式，一句話講清「什麼壞了、多嚴重」。「VIP 帳號結帳按確認後白畫面（必現、擋上線）」勝過「結帳有問題」。標題是工程師決定要不要現在看的唯一依據。
- **嚴重度與影響（講重點／有益）**：把它翻譯成對方在乎的後果——影響多少使用者、會不會掉錢、擋不擋上線。別只標一個 P1，說清楚為什麼是 P1。
- **環境（提問）**：裝置、版本、環境、帳號類型。定位問題的座標。
- **重現步驟（提問）**：按順序、標清預期 vs 實際、縮到最短路徑。能穩定重現的 bug 解決一半。
- **佐證（提問）**：截圖、錄影、錯誤訊息原文、log。讓對方不用回頭問你要。
- **已做努力（提問）**：你縮小範圍的發現——「只有 VIP、只有 iOS、一般帳號正常」。這往往直接幫工程師指向問題根源。

## 描述症狀，別下診斷

一個對 QA 特別重要的提醒：報告裡描述你「看到什麼」，別寫你「猜是什麼」。

- 差：「結帳壞了，應該是後端 API 掛了。」——猜錯的話，工程師可能照你的方向白查半天。
- 好：「按確認付款後畫面變白，沒有錯誤提示，網路面板顯示某請求回 500（截圖附上）。」——你給的是現象與客觀證據，根因讓懂的人判斷。

你的猜測有時有用（尤其你對系統熟），可以放，但要標明「這是我的推測」，跟客觀現象分開。把現象和診斷混在一起，是 bug 報告把人帶歪的常見原因。

## 對照：兩份報告，兩種命運

> 差：「VIP 結帳壞了，幫忙看。」
>
> 好：**標題**「[必現] VIP 帳號 iOS 結帳按確認後白畫面，擋上線」｜**影響**：所有 VIP 用戶無法完成付款，直接掉營收｜**環境**：正式環境 / iOS 17 Safari / VIP 帳號｜**重現**：① 加商品 ② 進結帳 ③ 選信用卡 ④ 按確認付款 → 白畫面｜**佐證**：截圖＋該請求回 500 的網路截圖｜**已做努力**：一般帳號正常、Android 正常，只有 iOS VIP 觸發。

第一份會被晾著、來回反問好幾輪；第二份工程師看完直接進入除錯，還被你縮好了範圍。差別不是努力程度，是有沒有把提問與講重點的框架套上去。

## 帶得走

- bug 報告同時是提問（請人定位修復）和講重點（讓人秒懂嚴重度）——兩套技巧的交會點。
- 標題用目標—差異講清「什麼壞了、多嚴重」；嚴重度翻譯成對方在乎的後果，別只標 P1。
- 環境＋重現步驟＋佐證＋已做努力，讓工程師不用反問就能開工。
- 描述症狀別下診斷；要放推測就標明「這是推測」，跟客觀現象分開。

最後一篇，把溝通拉到更高的層級：怎麼向上溝通、跨團隊協作，用風險與重點講品質。
