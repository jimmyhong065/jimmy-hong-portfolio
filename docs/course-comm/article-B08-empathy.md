# 同理心溝通：講對方在乎的好處、戒掉專業術語

有種溝通失敗特別冤：你明明聚焦了、也講了重點，對方還是沒接收到。原因不是你講得散，是你講的語言對方根本沒在用——你用測試圈、工程圈的術語，假設對方跟你有一樣的背景知識。但他沒有。

這背後有個常見的認知偏誤，叫「錯誤共識效應」：我們會不自覺假設別人懂的跟我們一樣多、在乎的跟我們一樣。戒掉這個假設，是同理心溝通的起點。

## 錯誤共識效應：你的常識不是對方的常識

對你來說再基本不過的概念，對方可能完全陌生：

- 你說「這個 API 沒做 idempotent，重試會重複扣款」——工程師秒懂，但對 PM 來說，這句話有一半是噪音。
- 你說「迴歸測試覆蓋不夠，這次改動有連帶風險」——QA 圈的人懂，但業務端聽到的可能只是「測試又在說有風險」。

問題不在對方笨或不專業，在於你預設了一個對方沒有的共識。每一個沒被解釋的術語，都是一道讓對方默默聽不懂、又不好意思打斷的牆。

## 翻譯：從「特色」到「對方在乎的好處」

同理心溝通的核心動作，是把「你領域的術語／特色」翻譯成「對方在乎的好處或後果」。同一件事，對不同人要講不同的版本：

| 你想講的（術語） | 對 PM 翻譯成 | 對業務／高層翻譯成 |
|---|---|---|
| API 沒做冪等，重試會重複扣款 | 使用者網路一卡、重按一下，可能被扣兩次錢 | 這是會上新聞、要退款道歉的客訴風險 |
| 迴歸覆蓋不足 | 這次改動可能弄壞旁邊沒改到的功能 | 上線後爆舊功能的機率變高 |
| 效能沒壓測 | 尖峰時段可能變慢或當掉 | 大促當天服務掛掉的風險沒人驗過 |

翻譯的準則：先問「對方的角色在乎什麼」——PM 在乎使用者體驗與時程，業務在乎營收與風險，工程師在乎技術細節。然後用他在乎的那個維度重講一次。

## 同理不是討好，是讓正確的資訊抵達

要澄清一個誤解：同理心溝通不是看人臉色、講對方愛聽的話。它的目的剛好相反——是讓「正確但逆耳」的資訊，能真的抵達對方、產生影響。

- 不做翻譯，你的風險警告卡在術語牆外，對方略過，出事還是出事。
- 做了翻譯，同樣的警告變成對方聽得懂、也在乎的後果，他才會認真權衡。

對 QA 來說這尤其關鍵。你最重要的訊息常常是壞消息、是別人不想聽的風險。同理心溝通不是讓壞消息變好聽，是讓壞消息被聽進去——用對方的語言講出對方在乎的後果，他才會把你的判斷當一回事。清楚勝過高深：能用白話講清楚的，就別用術語包裝。

## 帶得走

- 錯誤共識效應：別假設對方懂的、在乎的跟你一樣——你的常識不是對方的常識。
- 每個沒解釋的術語都是一道牆，讓對方默默聽不懂又不好意思打斷。
- 核心動作：把術語／特色翻譯成「對方角色在乎的好處或後果」，對不同人講不同版本。
- 同理不是討好，是讓正確但逆耳的資訊真的抵達——清楚勝過高深。

提問與講重點兩套內功都齊了，最後一個模組把它們合起來，用在 QA 最高頻的兩個場景：回報 bug 與向上溝通。
