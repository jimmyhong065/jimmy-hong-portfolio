# QA Lens admin MFA: predeployment security review

Reviewed: 2026-10-25. Scope: the local `3389ef5` admin MFA rollout, Cloudflare Pages Functions, deployment command, and the proposed Supabase RLS migration. This is a focused, read-only source review using Cloudflare's security-audit guidance mode. It is not a six-phase audit or a production penetration test.

## Confirmed from local source

1. **Deployment source can include unrelated edits (release blocker).** `package.json` runs `npm run build && wrangler pages deploy dist --project-name jimmy-hong-portfolio`. It has no clean-tree or commit check. On review, `git status --short` showed modified articles and `package.json`, plus untracked files. Building from this checkout would include any changed files imported by Vite or copied from `public/`; the deployment would not be a reproducible build of `3389ef5`. Release from an isolated clean checkout at a reviewed commit, inspect its status, and record the deployed commit. Do not use the current dirty checkout for the rollout.
2. **Admin identity has two configuration sources (verify before release).** Pages Functions compare the validated Supabase user's email with the runtime `ADMIN_EMAIL` binding in `functions/api/_auth.js`. The proposed `supabase/migrations/20261017_require_admin_aal2.sql` instead embeds one email in `public.is_admin()`. A mismatch could make Functions and RLS disagree about the administrator. Compare the production binding and migration target without copying the address into logs or this report.
3. **Admin Functions have a server-side MFA gate.** The reviewed subscriber, broadcast, email, push, upload, and R2 management routes call `requireAdmin`. That function asks Supabase `/auth/v1/user` to validate the bearer token, checks the returned email, then requires the token's `aal2` claim. Local unit tests cover absent, invalid, non-admin, and `aal1` tokens. These tests mock Supabase and do not prove production behavior.
4. **Two enrolled factors are a rollout condition, not a backend count check.** The frontend requires two verified TOTP factors before admin navigation. Functions and proposed RLS enforce `aal2`, which does not itself prove that two independent factors are enrolled. The runbook correctly puts two independent enrollments and two fresh-login checks before RLS activation; preserve that order.
5. **Local secrets are excluded from Git.** `.env.local` and `.dev.vars` are ignored and not tracked; their values were not read. This does not establish how production Pages secrets and preview bindings are configured.

## Environment checks required before deployment

- Confirm production Pages `SUPABASE_URL`, `SUPABASE_SERVICE_KEY`, and `ADMIN_EMAIL` bindings, R2 binding, and other runtime secrets in the Cloudflare dashboard. Store sensitive values as secrets and compare identity/configuration without printing values. Also verify preview environment bindings do not inadvertently use production write credentials.
- Confirm whether preview deployments are restricted with Cloudflare Access. Cloudflare documents that preview URLs are public by default; the repository cannot show the current dashboard setting. Access for previews does not automatically protect the main `*.pages.dev` domain.
- Run the proposed SQL against a non-production Supabase project and inspect **actual** `pg_policies`. Test `aal1` denial, `aal2` admin access, and non-admin denial against representative admin tables. The migration text alone cannot prove that a live policy does not bypass `is_admin()`.
- After an authorized deployment, use a real account to enroll two independent factors and test each in a separate fresh login. Verify an `aal1` request to one admin Function returns `403 MFA_REQUIRED`, then perform approved, reversible admin smoke tests. Do not send a broadcast as part of a smoke test.
- Verify the release through actual desktop and mobile pages, as required by `AGENTS.md`. HTTP success and a local build do not establish the reader-facing result.

## Live read-only follow-up (2026-10-25)

- Cloudflare Pages `jimmy-hong-portfolio` is connected to GitHub `main` with automatic production deployment. The current production deployment showed commit `bbb6f17`; the original local MFA commit `3389ef5` was 20 commits ahead of `origin/main` before this review's fix. A Git push would trigger the pending commit series, so it must be reviewed separately. No push or deployment occurred.
- Production Pages settings showed `ADMIN_EMAIL`, `SUPABASE_URL`, `SUPABASE_SERVICE_KEY`, the public client build settings, and an R2 `PHOTO_BUCKET` binding. Secret values were not opened, so identity equality and values remain unverified. The preview environment showed no separate variables or R2 bindings. Preview access currently offers a “restrict previews” action, indicating it is not restricted; public preview URLs should be considered during rollout planning.
- Supabase has one project, marked PRODUCTION, and no branches. No non-production database or local PostgreSQL/Docker/Supabase CLI was available, so the `aal1`/`aal2` SQL claim test remains unperformed. The production dashboard showed TOTP enabled, up to 10 factors, and the 15-minute AAL1 session limit on. It also showed an overall “Unhealthy” status with Realtime unhealthy while Auth was healthy; this does not itself establish an MFA failure.
- **Confirmed policy bypass:** live `public.faq_submissions` has `auth read submissions`, a `SELECT TO public` policy with `USING (auth.role() = 'authenticated')`. Any signed-in user can match it, independently of the `auth full access faq submissions` policy that calls `is_admin()`. All ten other authenticated admin policies inspected through the dashboard called `is_admin()`. The previous migration filtered only policies targeting exactly `authenticated` and the follow-up removed non-SELECT policies, which explains why this SELECT policy remained. This is an existing exposure, not an effect of the proposed MFA migration.
- Prepared `supabase/migrations/20261008c_remove_public_faq_submissions_read.sql` to remove that specific policy before rollout; also added the drop to the MFA migration and schema source. **None of these SQL changes have been executed on production.** The FAQ form uses the separate anon INSERT policy; admin listing uses the admin ALL policy. A real database verification after applying the fix is still required.
- The clean worktree was updated to the security-fix commit and passed the complete 55-file/429-test suite again. A build with the three existing public client settings passed; the worktree remained clean and `dist/index.html` retained the SHA-256 recorded above. No SQL execution test was possible without a separate PostgreSQL environment.
