# 從測試執行到專案上線：怎麼保證品質交付

不少人把「執行完所有案例」當成終點。但對團隊來說，那只是中間點。真正的終點是一個決策：**這個版本，能不能上線？** 從一堆紅紅綠綠的測試結果，到一個清楚的 go／no-go，中間有一段常被忽略卻最關鍵的工作。

## 缺陷分級：不是每個 bug 都同等重要

執行中一定會冒出缺陷。把它們全丟給工程師、要求「全部修完才能上」，是不專業的——時間不允許，也沒必要。缺陷要分級，讓修復的順序對齊風險：

- **嚴重度（severity）**：這個 bug 對系統的傷害多大。會讓資料錯亂、錢算錯、整個功能不能用的是高嚴重度。
- **優先級（priority）**：要多快修。高嚴重度但極少觸發的，優先級可能沒那麼高；中嚴重度但每個用戶都會踩的，優先級反而很高。

嚴重度與優先級是兩個軸，別混為一談。一個「首頁 logo 顏色錯」可能嚴重度低但優先級高（每個人都看到、傷品牌）；一個「極端條件下崩潰」可能嚴重度高但優先級看觸發機率。把這兩軸講清楚，工程師才知道先修哪個。

## 測試報告：講給決策者，不是講給自己

測試報告最常見的失敗，是寫成一份給測試自己看的流水帳——跑了幾個案例、過了幾個。決策者不在乎這些，他們在乎一件事：**現在上線，風險是什麼？**

一份對決策者有用的報告，講三件事：

1. **品質現況**：哪些功能可信、哪些有已知問題、哪些根本沒測到。
2. **剩餘風險**：如果現在上，最可能出什麼事、影響多大、有沒有緩解手段。
3. **建議**：基於上面兩點，你建議 go 還是 no-go，以及條件是什麼。

用數據支撐、用風險語言講，而不是用案例數量講。這是測試工程師從「執行者」走向「品質顧問」的關鍵一步。（怎麼用指標說服高層，模組 3 會深談。）

## Go／No-Go：把決策權交回給該負責的人

上線決策不該由測試一個人扛，也不該由工程或 PM 單方面拍板。健康的做法是：測試提供清楚的風險圖像，相關角色一起做知情決策。

- 測試的職責：把風險講清楚、講完整，不隱瞞也不誇大。
- 決策者的職責：在知情的前提下，決定承擔哪些風險、上不上。
- 共同的底線：上線後若出事，是「我們知道並選擇承擔的風險」，不是「沒人知道的盲區」。

最糟的上線不是「帶著已知風險上」，而是「帶著沒人知道的風險上」。測試的價值，就是把後者變成前者。

## 帶得走

- 測試執行是中間點，終點是一個 go／no-go 品質決策。
- 缺陷分兩軸：嚴重度（傷害多大）與優先級（多快修），別混為一談。
- 報告講給決策者：品質現況、剩餘風險、明確建議——用風險語言，不是案例數量。
- 上線決策是團隊的知情選擇；測試的價值是把「未知風險」變成「已知並承擔的風險」。
