# 測試技能與自動化的應用與趨勢

招募測試工程師時，最常被寫在需求上的是工具：會不會 Selenium、Playwright、Appium、會不會寫 CI。但用「會幾個工具」來衡量測試能力，就像用「會不會用手術刀」來衡量外科醫生——工具是手，判斷才是腦。

這篇要把這件事講清楚：自動化很重要，但它放大的是你的測試能力，不是取代它。

## 測試技能才是上限

自動化的本質，是把人想好的測試跑得更快、更多次。它忠實地放大你餵給它的東西——如果你餵的是設計精良的測試，它放大你的價值；如果你餵的是沒想清楚的測試，它只是讓你更快、更大規模地測錯東西。

所以真正的天花板不在工具，在前面幾個模組講過的設計能力：

- 看不看得出風險重心（E02）。
- 會不會用結構把案例擠出來（E04）。
- 分不分得清要驗哪些品質面向（E07）。

一個會設計、但只會手動測的人，價值高於一個自動化框架很漂亮、但案例設計很淺的人。因為前者只是慢，後者是系統性地測錯。工具可以學一週，設計能力要練很多年——這也是為什麼面試該問的是後者。

## 自動化划不划算：別什麼都自動化

自動化不是越多越好，它有維護成本。每一個自動化案例都是一筆要持續還的債——環境變了要修、UI 改了要改、flaky 了要查。所以該問的不是「能不能自動化」，是「自動化划不划算」。

值得自動化的，通常是：

- **穩定**：被測對象不會三天兩頭改，否則維護成本吃掉所有收益。
- **重複**：每次發版都要跑的回歸，跑越多次自動化越划算。
- **回歸價值高**：壞了影響大、需要每次都確認的核心路徑。

不值得自動化的陷阱：

- 還在頻繁變動的 UI——綁死在一個會一直改的東西上。
- 一次性的驗證——寫腳本的時間比手動測還久。
- 探索性、體驗性的判斷——這些本來就該靠人。

接回 E09 的精神：自動化是一筆投資，要能算出投報率。「為了自動化而自動化」是很多團隊把資源燒掉卻沒換到品質的原因。

## 趨勢：往下沉、往低維護、往 CI

撇開具體工具的更迭，自動化有幾個方向是穩定的：

- **金字塔下沉**：把大量驗證放到單元與 API 層，UI 自動化保持精簡。這比堆一大堆脆弱的 UI 測試健康得多（這正是 API 測試課的核心論點）。
- **低維護框架**：自我修復定位、更穩的等待策略、把 flaky 降下來——維護成本是自動化長期能不能活的關鍵。
- **進 CI 當品質門檻**：自動化最大的價值不是「能跑」，是「每次改動都自動跑、紅了就擋」。把測試接進 CI，讓它變成持續的防護網，而不是偶爾手動跑一次的擺設（內鏈 API 課 D17、k6 課 GitHub Actions 那篇）。

## 帶得走

- 工具是手、方法論是腦：自動化放大你的測試能力，不取代它。
- 測試技能才是上限——沒想清楚的測試，自動化只是更快地測錯。
- 自動化是有維護成本的投資：只自動化穩定、重複、回歸價值高的；算得出投報率才做。
- 趨勢三向：金字塔下沉、低維護框架、進 CI 當持續門檻。
