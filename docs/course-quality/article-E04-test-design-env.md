# 設計測試案例與建置測試環境，建立有效的防護網

把測試案例設計講成「憑經驗想」，是這行最大的浪費。經驗很重要，但經驗的問題是：它不可複製、不可檢查、會漏。測試設計方法存在的意義，就是把「靠想」變成「靠擠」——用結構把案例系統性地逼出來，連你沒想到的邊界都被逼到。

## 四個方法，把案例擠出來

不需要記一堆理論，掌握四個最常用的就能覆蓋大部分情境：

- **等價類劃分**：把輸入分成「行為相同」的群組，每群挑一個代表測。年齡 0–17、18–65、66+ 各測一個，不用每個數字都測。它讓你用最少的案例覆蓋最多的輸入空間。
- **邊界值分析**：bug 最愛躲在邊界。18 歲是成年的界線，那就測 17、18、19。`<` 寫成 `<=` 這種錯，只有邊界值抓得到。
- **決策表**：多個條件交織時用。「VIP × 庫存 × 優惠券」三個條件就有八種組合，決策表逼你把每種組合的預期行為都寫清楚，漏一格立刻看得出來。
- **狀態轉換**：有狀態的系統用。訂單從「待付款→已付款→已出貨→已取消」，要測的不只是每個狀態，更是「不該發生的轉換」——已出貨還能取消嗎？

這四個方法的共同點：它們不靠你聰明，靠結構。連菜鳥照著做，也能擠出資深憑直覺會漏的案例。

## 別只測 happy path

新手測試的通病是案例全集中在「正常流程」。但 bug 幾乎都住在異常與邊界：

- **異常輸入**：空值、超長、特殊字元、錯誤格式。
- **異常時序**：重複提交、操作到一半中斷、併發。
- **異常環境**：網路斷、伺服器慢、資源不足。

一個健康的案例集，異常與邊界案例應該明顯多於正常流程案例。如果你的案例九成都在測 happy path，這張防護網是漏的。

## 測試環境：結果可信的前提

再好的案例，跑在不可信的環境上也是白測。測試環境最常見的坑：

- **資料不對**：用一筆乾淨假資料測不出真實資料的髒問題。測試資料要能涵蓋真實世界的多樣與髒亂。
- **環境飄移**：測試環境跟正式環境配置不一致，測過的東西上線照爆。環境差異要被管理、被記錄。
- **狀態污染**：上一個案例改了資料，下一個案例踩到。案例之間要能獨立、可重置，否則紅綠都不可信。

一個原則：**測試結果的可信度，不會超過測試環境的可信度。** 環境是地基，地基歪了，上面測得再仔細都是空的。

## 帶得走

- 測試設計是「用方法擠案例」，不是「憑經驗想案例」——結構不靠聰明。
- 四把刀：等價類、邊界值、決策表、狀態轉換，覆蓋大部分情境。
- 健康的案例集，異常與邊界案例要明顯多於 happy path。
- 測試結果的可信度不會超過測試環境的可信度——資料、配置、狀態三者都要管。
